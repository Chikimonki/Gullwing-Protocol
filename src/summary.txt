## About That Special Auditor

You're right to ask. Today, the honest answer is: **most auditors can't read this**. But that's changing fast.

### The Current State
- Most compliance auditors are **document reviewers** — they check policies, not binaries
- CRA is forcing a shift toward **technical evidence**
- Brossard's whole thesis is that the industry needs tools that **translate binary reality into auditable evidence**

### What We Built Does Exactly That
The report translates low-level binary analysis into **plain language verdicts**:

```
[NX-STACK]       10/10  Non-executable stack enabled
[NO-WX-SEG]      10/10  No writable+executable segments
[CAVES]          10/10  No critical code caves
```

A compliance officer doesn't need to know what NX means — they see **10/10 PASS** or **0/10 FAIL**. The technical detail is there for the engineer who needs to fix it. The score is there for the auditor who needs to sign off.

That's the bridge Brossard talks about — **making binary truth accessible to governance**.

- All running on **Zig 0.13.0** with **zero warnings**

### What Each Tool Teaches

```

moabi-strings   →  "What does this binary reveal about its intentions?"
moabi-symbols   →  "What can this binary actually DO?"
moabi-hashdeep  →  "Has this binary been tampered with?"
moabi-report    →  "Should this binary be trusted under CRA?"
```

## Where To Take It Next

### Immediate Enhancements
1. **LuaJIT scripting layer** — we installed LuaJIT but haven't used it yet. This would let you write custom analysis rules without recompiling
2. **RELRO detection** — check for full/partial RELRO (GOT hardening)
3. **PIE detection** — verify position-independent executable
4. **FORTIFY_SOURCE detection** — check for stack protection
5. **Batch mode** — scan entire directories of binaries

### Medium Term
6. **ELF32 support** — currently ELF64 only
7. **Diff mode** — compare two versions of the same binary
8. **SBOM integration** — tie into Software Bill of Materials
9. **JSON output** — machine-readable reports for CI/CD pipelines
10. **Signature database** — known-good hashes for system binaries

### Brossard-Level Goals
11. **Relocation analysis** — understand how the binary links
12. **Control flow extraction** — map function call graphs
13. **Binary diffing** — section-level comparison between versions
14. **Capability policy enforcement** — define what a binary SHOULD import and flag deviations
